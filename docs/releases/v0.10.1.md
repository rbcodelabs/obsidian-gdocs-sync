## Every vault start no longer re-imports all your Google Tasks

If you had Google Tasks sync enabled, **every single time you opened your vault the plugin re-imported all of your tasks as if it had never seen them before.** You would get a flood of `Google Tasks: created "..."` notices, a fresh duplicate note for every task you had already imported, and — worse, because it is not confined to your vault — a fresh duplicate task pushed back up into Google Tasks itself. Open the vault ten times, get ten copies. ([#37](https://github.com/rbcodelabs/obsidian-gdocs-sync/pull/37))

This release fixes that.

### Why it happened

The plugin recognizes an already-imported task by reading a `gtasks_id` field out of the note's frontmatter. It read that field through Obsidian's metadata cache — the index Obsidian builds of every note's frontmatter, tags and links.

That index is not ready the instant a vault opens. It gets populated in the background over the first seconds of startup, and until a given file has been indexed, asking the cache about it returns *nothing* — which is indistinguishable from "this note has no `gtasks_id`".

The Tasks sync engine was started synchronously during plugin load, well before indexing finished. So it asked about every task note, got nothing back for all of them, and concluded that every previously-imported task was brand new. Both directions then did the wrong thing: the incoming path created a second local note instead of updating the existing one, and the outgoing path pushed each of those notes to Google as a new task.

Note that the bug had nothing to do with your data being wrong — the `gtasks_id` was sitting in the file the whole time. The plugin was simply asking a question too early to get a truthful answer.

### What changed

Two independent layers, either of which would have prevented the duplication on its own.

**1. Startup sync now waits until the vault is actually indexed.** A new `whenVaultIndexed()` gate holds the startup sync until the workspace layout is ready *and* the metadata cache reports its initial scan resolved, with a 10-second bounded fallback. The fallback is load-bearing rather than defensive: Obsidian's `resolved` event does not fire again if the cache happens to already be clean when the plugin subscribes, so without a second exit the sync could wait forever. If the plugin is unloaded while the deferred start is pending, it aborts instead of resurrecting itself.

Only the **startup** path is deferred. Syncs you trigger yourself from the command palette, and syncs after reconnecting your Google account, still run immediately — by then the cache has long been warm.

**2. The lookup no longer depends on the cache at all.** Resolving a note's task link is now tri-state — `linked`, `unlinked`, or `unknown` — instead of a boolean that collapsed "no link" and "cannot tell" into the same answer. When the cache yields nothing, it falls back to reading the file from disk and parsing the frontmatter directly.

If the link state still cannot be determined, the note is reported `unknown` and **skipped entirely — never pushed as new.** This fails closed on purpose: skipping a note that should have synced is a deferral that the next sync pass corrects, whereas pushing a note that was already linked creates a duplicate in someone's Google account that only they can clean up. The two failure modes are not symmetric, so the safe one is chosen deliberately.

As a side effect of the same pass, the task-id lookup builds its id-to-path index once per sync rather than rescanning the vault for every individual task.

## Existing duplicates are not cleaned up

**This release stops new duplicates from being created. It does not remove the ones earlier versions already made.** If previous vault starts left you with duplicate task notes in your vault or duplicate tasks in Google Tasks, those are still there and you will need to delete them yourself, in both places. There is no migration or de-duplication pass in this version, and the plugin will not attempt to guess which copy is the one you want to keep.

Cleaning up before or after updating both work — once you are on 0.10.1 the count stops growing either way.

## Verification

Observed on merged `main` ([`948a5d6`](https://github.com/rbcodelabs/obsidian-gdocs-sync/commit/948a5d66c38b8a33b9e9ef1087d11164a7ffdd7c)), in a clean worktree after `npm ci`:

- **387 passing tests across 24 files** (`npm test`), clean TypeScript (`npx tsc --noEmit`, exit 0), successful production build (`npm run build`, exit 0). CI unit tests green on the PR.
- **8 tests are specific to this fix.** Three are cold-cache regression tests against the sync engine: an already-imported note does not get a duplicate created, an already-linked note does not get a spurious remote task pushed, and a genuinely-unlinked note still pushes correctly (proving the fix did not simply disable the outgoing path). Five cover the startup gate itself: it waits for layout-ready, it resolves on `resolved`, it resolves via the timeout when `resolved` never fires, and it settles exactly once.
- **The two behavioral tests were confirmed failing against the unfixed engine before the fix landed** — so they demonstrate the bug, rather than merely describing the new code.
- **The fix is confirmed present in the shipped `main.js`**, not compiled out: `whenVaultIndexed` appears in the built bundle. This check exists because v0.8.0 once shipped a feature that was absent from the published bundle; it is verified rather than assumed.

## Not verified

- **No live vault restart with a real connected Google Tasks account was exercised in this release's gate.** The evidence is the unit suite driving the engine and the readiness gate directly, with a simulated cold cache and stubbed Google API. The mechanism is understood and tested, but "no duplicates on a real vault open" is an argument here, not an observation.
- The 10-second timeout fallback is verified with fake timers, not against a genuinely slow real-world index.
- The fix's behavior on a very large vault — where indexing might exceed the 10-second bound and the sync would proceed on a still-warming cache — has not been measured. Layer 2 (the disk-read fallback) is what covers that case, and it is unit-tested, but not at scale.
- No UI changed in this release, so there is no visual verification to report.
